# Known problems and fixes

Read this when Dynare or MATLAB reports an error or a result looks wrong: scan this file first. If an
entry matches the symptom, apply its fix; do not derive it again.

This file is a read-only list of problems that were solved in real projects. `references/debugging.md`
teaches how to diagnose general and structural errors (Blanchard-Kahn conditions, steady state,
singular Jacobian, syntax) and holds the final checklist. This file records specific problems with
ready fixes.

Do not edit this file. When you solve a problem that is not here, describe the symptom, the cause and
the fix in the report to the user (SKILL.md "Report").

Each entry gives the symptom, the cause, the fix, and the scope: the Dynare version where the problem
was observed, and what Dygnosis reports for it. "Not rechecked with 7.2" means nobody has run the
reproducer under Dynare 7.2 yet.

A "lag-only exogenous variable" below is an exogenous variable that appears in the model only with a lag,
for example `rstar(-1)` in a Taylor rule with an implementation lag.

---

## `heterogeneity_solve` crashes: `eq` undefined in `process_jacobian_block`

- **Symptom:** a heterogeneous-agent model crashes in `heterogeneity_solve`. The stack ends in
  `process_jacobian_block` with `eq` undefined.
- **Cause:** the aggregate block has a lag-only exogenous variable. Dynare adds an auxiliary equation for
  it, and the row of that equation is greater than `M_.orig_endo_nbr`. `heterogeneity_solve` walks the
  Jacobian with `find()`, which returns entries column by column. If that exogenous variable is declared
  first in `varexo`, its auxiliary row comes before any ordinary equation row, and the loop uses `eq`
  before it has a value.
- **Fix:** declare every lag-only exogenous variable **last** in `varexo`, as the official example
  `<dynare-root>/examples/heterogeneity/hank_one_asset.mod` does (`varexo G markup rstar;`, with
  `rstar(-1)` in the Taylor rule):

  ```dynare
  // Correct: the lag-only rstar is declared last
  varexo G TR markup rstar;     // rstar(-1) enters the Taylor rule
  // Wrong, crashes: varexo rstar G TR markup;
  ```

- **Scope:** observed with Dynare 7.1. In Dynare 7.2, `+heterogeneity/solve.m` still sets `eq` only for
  rows up to `M_.orig_endo_nbr` (code read, not run). Dygnosis reports nothing: the declaration order is
  legal.
- **More:** `references/heterogeneity.md`, pitfalls section.

## Plain model: `disp_dr` / `subst_auxvar` crash with a lag-only exogenous variable

- **Symptom:** a plain (not heterogeneous) model with a lag-only exogenous variable such as `rstar(-1)`
  runs `stoch_simul` and crashes while it prints the policy functions. MATLAB reports that an indexing
  expression produced 2 values (the wording depends on the MATLAB version and language).
- **Cause:** for the lagged exogenous variable Dynare creates a lag auxiliary variable. In `disp_dr`,
  `subst_auxvar` looks it up in `M_.aux_vars` and finds 2 entries.
- **Fix:** replace the lagged exogenous variable with an endogenous AR(1) process driven by an
  innovation, and use its current value in the rule:

  ```dynare
  var rstar_sh; varexo eps_rstar;
  [name='Taylor rule'] (1+r_ss+rstar_sh+phi*pi)/(1+pi(+1)) - 1 - r;
  [name='MP shock AR(1)'] rstar_sh - rho_r*rstar_sh(-1) - eps_rstar;
  ```

  In a heterogeneous model the same lagged exogenous variable crashes in `heterogeneity_solve`
  instead, with a different fix (previous entry).
- **Scope:** observed with Dynare 7.1; not rechecked with 7.2. Dygnosis reports nothing: a lagged
  exogenous variable is legal.

## IRF field not found: `oo_.irf`

- **Symptom:** a post-processing script fails on `oo_.irf.Y_G`: the field does not exist.
- **Cause:** `stoch_simul` stores IRFs in `oo_.irfs` (plural), not `oo_.irf`.
- **Fix:** use `oo_.irfs.<var>_<shock>`. If unsure, check with `disp(fieldnames(oo_))`, or use
  `get_irf('<shock>', '<var>')`. Heterogeneous models are different (next entry).
- **Scope:** all versions; the Dynare 7.2 manual documents `oo_.irfs` with the name convention
  `VARIABLE_NAME_SHOCK_NAME`. MATLAB code; Dygnosis does not read it.

## HANK IRFs: where `heterogeneity_solve` stores them

- **Symptom:** after a heterogeneous-agent model runs, `oo_.irfs` has no IRFs.
- **Cause:** `heterogeneity_solve` stores the aggregate dynamics as sequence-space Jacobians in
  `oo_.heterogeneity.dr.G.<var>.<shock>`, a T×T matrix (T is `truncation_horizon`). Entry `(t,s)` is the
  response of `<var>` in period `t` to a unit deviation of `<shock>` in period `s`.
- **Fix:** the IRF to a one-time shock in period 1 is the **first column**. For output `Y` and a shock
  named `G`: `oo_.heterogeneity.dr.G.Y.G(:,1)` (the first `G` is the field name, the last `G` is the
  shock). This is the response per unit of shock; multiply by the shock size. In Dynare 7.2,
  `heterogeneity_simulate` (after `heterogeneity_solve`) stores IRFs in `oo_.irfs` as
  `<var>_<shock>`, like `stoch_simul`.
- **Scope:** observed with Dynare 7.1; field layout and `heterogeneity_simulate` output confirmed in the
  Dynare 7.2 manual. MATLAB code; Dygnosis does not read it.
- **More:** `references/heterogeneity.md`, IRF section; `references/matlab-workflow.md`.

## Analysis or plotting script: `Undefined function 'range'`

- **Symptom:** a self-written analysis or plotting script fails on some computers: `range` is undefined.
- **Cause:** in MATLAB, `range` (spread of values) comes from the Statistics and Machine Learning
  Toolbox, which not every installation has.
- **Fix:** use base MATLAB: `max(x)-min(x)`, or `diff(ylim)` for an axis. In your own post-processing
  code, prefer base functions to toolbox functions.
- **Scope:** MATLAB, independent of the Dynare version. Not a Dynare or Dygnosis problem.

## Pure exogenous variable treated as positive in the steady state: residual not zero

- **Symptom:** `resid;` shows a nonzero residual for a government budget equation or similar. Dynare
  reports no error.
- **Cause:** `G`, `TR` and similar are pure exogenous variables (not endogenous AR processes). Their
  steady-state value is 0, but the steady-state equations use positive values for them.
- **Fix:** for `Tax = r*B + G + TR`, write the steady state as `Tax_ss = r_ss*B` (because `G = TR = 0`),
  not `+ G_ss + TR_ss`. If the variable must have a positive steady state, write it as an endogenous
  process around a steady-state parameter (R3).
- **Scope:** modeling error; not version-specific. Dygnosis does not compute residuals; only `resid;`
  shows it.

## Fiscal multiplier about 0.01 (wrong number, no error)

- **Symptom:** a RANK balanced-budget government spending multiplier comes out at about 0.01. The model
  runs clean, with no error.
- **Cause:** post-processing. The normalization omits the steady-state share `1/g_y`, a percentage IRF is
  used as a ratio of levels, or `Scale` divides by 100 once too often. Analytically the balanced-budget
  multiplier is about 1.
- **Fix:** after the solve, print the multiplier and the analytical benchmark with `fprintf`
  (balanced-budget spending about 1, Ricardian transfers 0) before you trust the figure.
- **Scope:** post-processing; not version-specific. No tool reports it.
- **More:** `references/debugging.md`, "Wrong numbers without an error"; `references/matlab-workflow.md`,
  "Check against analytical benchmarks".

## Perfect foresight fails: singular Jacobian from a forward-looking pricing block with `x(-1)`

- **Symptom:** `perfect_foresight_solver` reaches `maxit`, every homotopy share fails, and MATLAB repeats
  `Matrix is singular to working precision` (`lin_solve`, then `sim1`), ending with `Failed to solve
  perfect foresight model`. `check;` already shows a sign: the eigenvalue table has huge spurious
  eigenvalues (about 1e17 to 1e51), but the rank condition is still verified, so it is easy to miss.
- **Cause:** a forward-looking asset pricing equation has both a lead and the price of the previous
  period, for example a perpetuity `RL = (1+kappa_L*QL)/QL(-1)` with
  `1+zeta = betta*E[(C(+1)/C)^(-sigma)*RL(+1)]`. The `QL(-1)` recursion creates nearly infinite
  generalized eigenvalues in the stacked system, and the Jacobian is singular. The ZLB and `lmmcp` are
  not the cause: the same scenario without `lmmcp` also fails, which isolates the block.
- **Fix:** first decide whether the block **feeds back** into the real economy. If it is only a reported
  long rate or term structure (for example, QE works through `zeta`, the capital Euler equation and
  investment, and the long bond enters no real equation), do not tune the solver. Reduce the block to a
  static identity, for example the long nominal rate `RL = R*(1+zeta);`, and remove `QL` and its
  forward-looking Euler equation. The singularity disappears and the solver converges in a few
  iterations. Under the ZLB `R` is fixed, so `RL` moves only with the `zeta` that QE lowers, which also
  makes the mechanism clearer.
- **General rule:** a forward-looking equation that contains `x(-1)` easily makes the perfect-foresight
  Jacobian singular. For a block without feedback, simplify before you tune. If the block must keep its
  dynamics (it does feed back), use a helper variable for the price-level difference, or the model
  option `differentiate_forward_vars` (`model(differentiate_forward_vars);`), to help convergence
  (`references/perfect-foresight.md`, singular Jacobian and permanent shock sections).
- **Scope:** observed with Dynare 7.1; not rechecked with 7.2. Numerical; Dygnosis does not decide
  solver convergence.

## Parameter initialization: `Namespace-qualified symbol pp.x not allowed in this context`

- **Symptom:** the `.mod` file tries to use parameters computed in the MATLAB workspace (for example an
  external script computes derived or steady-state coefficients). It writes `alppha = pp.alppha;`
  (`pp` is a struct), or `var eps = pp.sig^2;` in a `shocks` block. The preprocessor stops with
  `Namespace-qualified symbol pp.alppha not allowed in this context`.
- **Cause:** the Dynare preprocessor does not accept a struct field (`a.b`) as a value in parameter
  initializations or in `shocks` blocks. It takes only declared names and numbers there.
- **Fix:** let the driver script write every value to inject into a numeric include file, and pull it
  into the `.mod` with `@#include`:

  ```matlab
  % run_model.m: after computing all deep and derived parameters
  fid=fopen('model_params.inc','w');
  for k=1:numel(names), fprintf(fid,'%s = %.15g;\n', names{k}, eval(names{k})); end
  fclose(fid);
  dynare model.mod noclearall
  ```

  ```dynare
  parameters alppha betta ... sig_z ...;   // declare first
  @#include "model_params.inc"             // one numeric assignment per line
  ...
  shocks; var eps_z = sig_z^2; end;        // use the declared parameter, not pp.sig_z
  ```

  Now every right-hand side is a number or a declared parameter, and the preprocessor accepts the file.
  Compute steady-state coefficients that need `fzero`, `normcdf` and similar in the driver too, and
  write them into the `.inc` file. Worked example: `references/model-archive/swff/run_swff.m` writes
  `swff_params.inc`, which `swff.mod` includes.
- **Scope:** Dynare refusal; the 7.2 preprocessor has the same message. Dygnosis reports it as E275
  (Error). Generate `model_params.inc` before you run Dygnosis or Dynare; a missing include is E061.
  A qualified function call such as `pkg.foo(1)` is a different form (see `dynare_explain` for E275).

## Linear Smets-Wouters-type estimated models: IRFs 100 times too large

- **Symptom:** a replication of a Smets-Wouters or FRBNY-type estimated model plots IRFs with
  `plot_irfs_pub` and its default `Scale=100`, and shows implausible sizes (investment falls 180%, output
  30%). Blanchard-Kahn conditions and the steady state pass; only the size is wrong.
- **Cause:** in these papers the observation equations are `obs = 100*(model var)`, so the model
  variables are log deviations in decimals. The standard deviations in the parameter table (0.05 to 3)
  are innovations in **percentage points**. `var eps = sigma^2` with the table value treats percentage
  points as decimals and makes the variables 100 times too large; `plot_irfs_pub` with its default
  `Scale=100` (which assumes decimals and converts to percent) multiplies again. Choose one consistent
  unit system:
  1. variables in decimals, innovations `sigma/100`, plots with `Scale=100`; or
  2. variables in percentage points, innovations `sigma` (table value), plots with `Scale=1`.
- **Fix:** choose one system and check it: a one-standard-deviation **monetary policy shock** lowers
  output by about 0.3 to 0.6% and raises the policy rate by about 0.1 to 0.2 percentage points. If the
  sizes are far from this, suspect the factor of 100 first. Simplest: keep the table `sigma` (variables
  in percentage points) and call `plot_irfs_pub(...,'Scale',1)`.
- **General rule:** an observation equation with `100*` means the model variables are decimals; a
  `sigma` of about 0.1 to 3 means percentage points. The two must match, and `Scale` follows the unit of
  the variables (decimals: 100; percentage points: 1).
- **Scope:** units; not version-specific. No tool reports it.
- **More:** `references/publication-plots.md`, `Scale` parameter.

## BGG/CMR financial friction steady-state coefficients (`zeta_nRk` and others): translate DSGE.jl

- **Symptom:** a replication with BGG or Christiano-Motto-Rostagno financial frictions (external finance
  premium, entrepreneurial net worth, spread equation) needs the `zeta` coefficients of the net-worth
  equation (`zeta_nRk/zeta_nR/zeta_nqk/zeta_nn/zeta_nsigw/zeta_spsigw`). The paper does not give them:
  it shows only the reduced-form linear equations, and the coefficients are functions of the deeper
  costly-state-verification (CSV) steady state.
- **Cause:** the BGG steady state determines the coefficients implicitly. Given the default probability
  `Fstar`, the survival rate, the steady-state spread `spr` and the spread-to-leverage elasticity
  `zeta_spb`, first solve for sigma_omega with `fzero`, then evaluate a set of Gamma/G functions and
  their derivatives. Derivations by hand go wrong easily.
- **Fix:** translate two parts of the **FRBNY DSGE.jl m990** source into MATLAB helper functions (no web
  search for formulas needed): `financial_frictions.jl` (`zeta_spb_fn/zeta_bw_fn/zeta_zw_fn/nk_fn/mu_fn/
  G/Gamma` and their derivatives) and `steadystate!` in `m990.jl` (the `zeta_n*` and `zeta_sp*`
  net-worth coefficients). In the driver script, solve for sigma_omega with `fzero`, compute all `zeta`
  coefficients, and write them into the `.inc` file (previous `@#include` entry). A translation exists in
  the archive: `references/model-archive/swff/swff_ff_coeffs.m`, called from `run_swff.m`. Steady-state
  checks: the default probability equals `Fstar`; `nk*` (net worth over capital) is between 0.4 and 0.8;
  `r_k*` is about 0.03 to 0.04 (standard quarterly rental rate). Use the **gross quarterly spread** for
  `spr`: `(1+SP_annual/100)^(1/4)` or `1+SP/400`.
- **General rule:** when you cannot derive the coefficients of a reduced-form linear block, find an
  authoritative code implementation of that model first (DSGE.jl, a Dynare replication) and translate
  it line by line. This is faster and safer than reverse-engineering the paper.
- **Scope:** modeling; not version-specific.
- **More:** `references/catalog-lookup.md` (programming library; authoritative implementations first).
